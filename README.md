# favorart.github.io

Personal page of Kirill Golikov: https://favorart.github.io

The site is generated by `build.py` (Python + `markdown`, `pyyaml`, `pygments`) and deployed by
GitHub Actions (`.github/workflows/pages.yml`) on every push to `main`, daily, and on manual run.

## Layout

| Path | What |
|---|---|
| `content/home.en.html` | home page body (sections, CV preview, contact form) |
| `content/cv.en.html` | the full CV page `/cv/` |
| `i18n/en.yml` | UI strings; one file per language (`prefix: /ru` etc. for non-default ones) |
| `templates/` | base layout and partials — the design lives here and in `assets/site.css` |
| `assets/site.css` | the one stylesheet |
| `content/teasers.yml` | card teasers per item and language (≤140 chars, break off with "…"); shown instead of the summary |
| `posts/<yyyy-mm-slug>/index.md` | LinkedIn posts and the site's own articles (+ their images in the same folder) |
| `sources.yml` | external articles and courses, pulled from other repos at build time |
| `covers/<slug>/` | cover options for external content; chooser page: `/writing/covers/` |
| `tools/make_covers.py` | generates 3 SVG cover options |
| `tools/check_links.py` | checks the built site for broken links/images |

## Build locally

```sh
pip install -r requirements.txt
python build.py            # -> _site/  (add --offline to skip fetching external repos)
python tools/check_links.py _site
python tools/layout_check.py _site --chrome   # layout in a browser: 5 languages × 375/768/1280 × light/dark
python -m http.server -d _site 8000
```

`tools/layout_check.py` (needs `pip install playwright`; in CI it uses Playwright's Chromium, locally `--chrome`
uses the installed Chrome) fails on sideways scroll, touch targets under 40 px on phones, wrapped dates, menu items
and buttons, and short words left at a line end. `.github/workflows/layout.yml` runs it on every push and pull
request; it does not block the deploy.

## Add a LinkedIn post

1. Create a folder `posts/2026-12-short-slug/` (the page will be `/writing/short-slug/`).
2. Put `index.md` there:

   ```markdown
   ---
   title: "Post headline"
   date: 2026-12-01
   lang: ru
   summary: "One or two sentences for the card."
   source: linkedin
   original_url: https://www.linkedin.com/posts/...
   cover: cover.jpg          # an image in this folder; omit and run tools/make_covers.py for SVG options
   card_cover: cover-1.svg   # optional: another picture for cards (e.g. when cover.jpg is a portrait photo)
   tags: [cpp, performance]  # optional, the post's hashtags
   ---

   Post text in Markdown. Images: ![alt](picture.png) with picture.png in this folder.
   ```

   Note: a line starting with `#word` is a heading in Markdown — write `\#word` for a hashtag.
3. Commit and push — the Action rebuilds the site.

### The site's own article

An article written for the site itself goes the same way into `posts/<yyyy-mm-slug>/index.md`, but without
`source` and `original_url`: it is listed as an Article, has no "LinkedIn post" label or link to an original, and
ends with the "Send feedback" button. Translate it like any post (see Translations).

### Rules for copying a post

- **Copy the whole post, including its continuation in the comments.** LinkedIn limits a post's length, so a
  long post often ends with "Продолжение в комментарии…", "Далее ниже…" or similar and goes on in the
  author's own comments (and replies to them). Collect every such comment by the author, in order, and
  append each one to the post text as a separate part, with no "from the comments" heading — the reader
  should get one continuous text. Drop only the "continued below" markers themselves.
- Comments by other people are not copied.
- Only some comments are visible without signing in to LinkedIn. If the continuation is hidden, open the
  post while signed in (or ask the author for the text); never publish a post that stops at "continued in
  the comments".
- Keep the text verbatim (fix nothing but obvious Markdown breakage); images of the post go into the
  folder, the first one as `cover.jpg`.
- `original_url` is the full `linkedin.com/posts/...` URL without tracking parameters (`?utm_…`, `rcm=`).
- Links are hidden behind names: a reading list "Title -- note https://…" becomes `[Title](https://…) -- note`;
  `lnkd.in` short links are replaced by their targets (a link to an earlier post that is on the site → its page).

## Translations

The site is in en / es / ru / sr / uz. The page around every text is translated (`i18n/`, `content/`); posts
and articles (Writing), and the abstracts of papers, are translated into the other languages and kept as **one
file per text and language**, updated in place (older versions exist only in git history):

```
translations/<slug>/<lang>.md
```

`source_hash` in its front matter is the version of the original it was translated from (build.py
`source_hash`: sha256 of the normalized Markdown, 8 hex digits). Front matter: `title`, `summary`, `source`,
`source_lang`, `source_hash`, `translated`, `translator`, `reviewed` (date of the independent review — files
without it are not published); for a paper also `keywords`, and the body is the abstract.

On every build, for each text × language:

| File | Page shows |
|---|---|
| reviewed, `source_hash` = current original | the translation, with "Translated … Original: <language>" |
| reviewed, original changed since | the translation + "The original has been updated since this translation" |
| missing or not reviewed | the original text |

The build prints `translations: N up to date, M outdated, K missing`. Tools:

```sh
python tools/translations.py status              # table: ok / missing / outdated / unreviewed
python tools/translations.py source <slug>       # the original + its hash
python tools/translations.py new <slug> <lang>   # creates the file, or re-stamps an outdated one in place
```

When a post or article is added or changed, every missing/outdated translation is made and reviewed in the
same commit — the procedure is in `CLAUDE.md`; agreed terms in `docs/translation-glossary.md`.
Courses are not translated (their lectures are in Russian); papers have RU + EN abstracts.

## Add a project

Projects (`/projects/<slug>/`) are written for the site itself, in every language:

```
projects/<slug>/project.yml   # name (= the repo name, the title everywhere), date, date_label, cover, demo_url,
                              # links: [{url, label}] — label may be {en: …, ru: …}
projects/<slug>/<lang>.md     # front matter tagline (subtitle), summary, kind (card label); body = page text
```

The build fails if a language file is missing. Write `en.md` first, then the other languages with an
independent review (as for translations, see `CLAUDE.md`). Covers: `python tools/make_covers.py covers/<slug>
<motif> "<title>" "<kicker>"` plus `--lang xx --author "Name"` per language (motifs for projects: wave, net,
btree, heap, cpu, code).

## Add an external article or course

Add an entry to `sources.yml` (`articles:` → `/writing/<slug>/`, `courses:` → `/courses/<slug>/`)
with `repo`, `branch`, `path`, `title`, `date`, `summary`. Nothing is copied: the Markdown is fetched at
build time and its relative links/images point back to the source repo. For a cover run
`python tools/make_covers.py covers/<slug> <motif> "<title>" "<kicker>"` (motifs: pi, robot, tree, cpp,
cpu, code, wave, net, btree, heap), set `cover: covers/<slug>/cover-1.svg`, then pick the final option on `/writing/covers/`.
The tool also writes text-free twins (`cover-N-plain.svg`); the article page shows the twin of the chosen cover
above the title (`--plain-only` regenerates just the twins).

## Add a paper or a conference abstract

`sources.yml` → `papers:` (page `/writing/<slug>/`, the PDF stays on the publisher's site). Common fields:
`slug`, `title`, `authors`, `year`, `pdf`, `lang`, `summary`, `abstract` (the page body), optional `keywords`,
`title_en`/`summary_en`/`abstract_en`/`keywords_en` when the publisher gives an English version, `cover`.
- Journal paper: `journal`, `journal_en`, `journal_short`, `volume`, `issue`, `pages`.
- Conference abstract (тезисы доклада): `conference`, `conference_en`, `conference_short` (per language, without the
  year: "Ломоносов"), `section`, `section_en`, `collection` (the collection's record after "//", as the
  publisher gives it), `date` (the conference). Tagged "Тезисы / Talk abstract" and filtered with the papers.

Add it to `content/cv.<lang>.html` → Publications in every language, then translate the abstract like a post.

## Analytics

GoatCounter (`GOATCOUNTER_CODE` in `build.py`, dashboard https://favorart.goatcounter.com), no cookies and no
personal data, so no consent banner. Page views of an item in any UI language count as one path. Besides page
views, `templates/base.html` sends events (Dashboard → "Events"):

| Event | When |
|---|---|
| `click/contact` | a link to `#contact` |
| `form/contact-sent` | the contact form is submitted (after the browser's validation) |
| `out/<host>/<path>` | an outgoing link (LinkedIn, GitHub, journals…) |
| `download/<file>` | a link to a .pdf/.zip/.docx/.pptx |
| `read-50/<page>`, `read-90/<page>` | scrolled to half / almost the end (pages longer than 1.5 screens) |
| `time-1m/<page>`, `time-3m/<page>` | the tab was visible on the page for 1 / 3 minutes |

Links to the site in posts carry `?ref=linkedin&utm_campaign=<post-slug>`: LinkedIn sends no referrer, and
GoatCounter reads `ref` as the source and `utm_campaign` as the campaign.

Weekly report: `.github/workflows/weekly-report.yml` runs `tools/weekly_report.py --send` every Monday and
e-mails the past week's stats through Web3Forms to the contact form's inbox (not published anywhere: the repo
and its Actions logs are public). Secrets: `GOATCOUNTER_API_TOKEN` (GoatCounter -> your name in the top menu ->
API -> only "Read statistics", only this site) and `CONTACT_FORM_KEY`.

"What's new" digest: `.github/workflows/site-digest.yml` runs every Sunday and e-mails (same Web3Forms channel)
what changed on the Russian pages over the week, in plain words for readers: new pages with their summary and
link, edited paragraphs as "Было / Стало", removed ones (`tools/site_digest.py`; no commits, no code, page
chrome skipped). Last week's text is the previous scheduled run's artifact. Try it by hand: Actions -> the
workflow -> Run workflow (`end` = last day of a past week, `days`, `send` off prints the digest in the log instead of e-mailing it), or locally
`python tools/site_digest.py snapshot <site> old.json` for two builds, then `diff old.json new.json`.
